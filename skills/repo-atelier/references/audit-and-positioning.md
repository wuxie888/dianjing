# 仓库审计与产品定位

## 1. 先确定真正的仓库

依次确认：

1. 用户指出的目录是否含 `.git`。
2. `git rev-parse --show-toplevel` 返回什么。
3. `origin` 是否对应用户要装修的公开对象。
4. 当前分支、提交、Tag 和工作区修改。
5. 是否存在另一个干净 checkout、构建产物目录或只放素材的同名目录。

目录不是 Git 仓库时，先寻找真实 checkout 或公开远端。不要在素材目录里擅自初始化新仓库。

## 2. 建立事实底稿

用源码和实际产物回答，不依赖 README 自我描述：

| 事实 | 优先证据 |
| --- | --- |
| 产品类型 | 源码入口、构建配置、运行产物 |
| 已实现能力 | 核心源码、测试、真实界面、Release |
| 安装方式 | 包清单、插件清单、安装脚本、官方发布渠道 |
| 当前版本 | Tag、Release、清单版本、CHANGELOG |
| 可运行程度 | 本轮运行、历史可复现日志、CI；标注证据日期 |
| 许可证 | 根 LICENSE、包元数据、素材和依赖许可证 |
| 维护状态 | 提交、Issue、PR、CI、Release |
| 分发状态 | 真实市场/商店页面、公开下载或安装验证 |

将内容分为：

- 直接观察
- 仓库或作者声称
- 独立验证
- 合理推断
- 未验证

装修文案只能把证据支持的状态写成事实。

## 3. 识别产品类型

### App 或在线产品

重点展示真实界面、核心任务、运行平台、权限、下载/访问入口和首次成功。

### CLI 或开发者工具

重点展示一个真实命令、输入输出、安装方式、兼容环境、配置和失败恢复。不要用大段品牌图遮住可复制的使用示例。

### 库、SDK 或框架

重点展示最小集成代码、API 形态、支持矩阵、稳定性、版本策略和迁移方式。

### Agent Skill 或插件

分开能力本体与分发层。展示明确触发方式、真实任务示例、安装/升级、新任务加载、权限和外部服务边界。

### 内容、研究或数据项目

重点展示范围、方法、数据来源、更新日期、许可证、可复现方式和结论边界。

## 4. 提炼一句话定位

优先使用这个结构：

```text
[产品名] 帮助 [目标用户] 把 [输入/困难] 变成 [输出/结果]，从而 [可采取的行动]。
```

避免：

- 只堆“AI 原生、平台无关、下一代”等抽象标签
- 用技术栈代替用户价值
- 把一个亮点能力冒充完整产品
- 把尚未验证的愿景写成当前功能

## 5. 定义第一次成功

第一次成功不是“安装完成”。按产品类型定义一个用户可以独立完成的真实结果：

- App：完成一个核心任务并看到结果
- CLI：执行一个安全命令并得到可核对输出
- 库：运行最小示例或测试
- Skill/插件：在新任务正确调用并完成一个真实请求
- 数据项目：复现一个查询、图表或结论

README、上手文档、截图和动图应共同服务这条路径。

## 6. 形成视觉依据

在设计前明确：

- 产品气质：精确、温暖、实验、专业、极简、戏剧化等
- 必须保留的品牌资产
- 真实产品中已经存在的颜色、字体、形状和图标线索
- 一个最适合动态展示的价值瞬间
- 不应模仿的竞品身份与商标

设计系统可以借鉴布局、节奏和交互原则，不复制其他品牌的身份、文案或专有视觉。
