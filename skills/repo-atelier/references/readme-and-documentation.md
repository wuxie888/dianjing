# README 与仓库文档

## 目录

- README 的任务与信息顺序
- Hero、能力展示与安装升级
- 文档分层与治理文件
- 双语与写作标准

## README 的任务

README 是产品首页，不是文件目录，也不是安装命令容器。让首次访问者依次回答：

1. 这是什么？
2. 为什么与我有关？
3. 它真的存在吗？
4. 能做什么，不能做什么？
5. 怎样第一次成功？
6. 当前值得信任到什么程度？

## 推荐信息顺序

根据产品删改，不机械保留所有章节：

1. Logo、产品名与一句话价值
2. Hero 或真实核心演示
3. 目标用户和典型问题
4. 核心能力或工作流
5. 真实截图、输出、GIF 或视频
6. 当前状态与关键边界
7. 安装或访问
8. 第一次成功
9. 常见用法
10. 升级、排错和卸载
11. 测试与验证状态
12. 架构或仓库结构
13. 安全、隐私、许可证和贡献
14. 维护、支持与 Release

安装可以提前，但只有在产品价值已经显而易见或访问者明确属于开发者受众时。

## Hero 标准

Hero 必须在首屏完成三件事：

- 识别品牌
- 说清用户结果
- 提供一个真实证据或下一步

可选择：

- 静态品牌 Hero
- 带静态首帧的动态 Hero GIF
- 真实产品界面与短标题
- 一条最小命令和输出

不要使用无法对应真实产品的虚构 UI。不要让大图把产品说明推到数屏之后。

## 能力展示

每项能力使用“任务 → 行为 → 结果”，不要只列抽象名词：

```text
输入一个真实仓库
→ 检查源码、许可证和维护状态
→ 得到是否值得使用或二开的判断
```

优先展示 3–6 个决策级能力。次要能力进入详细文档。

## 安装、升级与重新加载

明确区分：

- 第一次安装
- 已安装用户升级
- 本地缓存刷新
- 产品或插件重新加载
- 卸载

命令必须从当前工具或官方文档核验，不从旧对话复制。涉及第三方市场、脚本、远程服务或账号时说明信任边界。

## 文档分层

只创建真正有独立读者和任务的文档：

| 内容 | 推荐位置 |
| --- | --- |
| 产品入口 | `README.md` |
| 第一次成功 | `docs/GETTING_STARTED.md` |
| 常见阻塞 | `docs/TROUBLESHOOTING.md` |
| 产品边界 | `PRODUCT.md` 或 README |
| 维护和发布 | `HANDOFF.md` 或维护者文档 |
| 版本变化 | `CHANGELOG.md` |
| 稳定发布说明 | `docs/releases/<version>.md` 或 GitHub Release |

不为了“看起来完整”创建无人使用的空文档。

## 治理文件

根据公开程度和贡献模式评估：

- LICENSE
- CONTRIBUTING
- SECURITY
- CODE_OF_CONDUCT
- SUPPORT
- Issue / PR 模板
- Citation

存在文件不等于内容正确。核对项目名、联系方式、支持范围、漏洞报告路径和许可证一致性。

## 双语

双语是同一信息架构的两个入口，不是两套产品：

- 两种语言互相链接
- 章节顺序与状态一致
- 安装命令、版本和链接一致
- 不用机器直译破坏产品语气
- 版本更新时同步检查

若目标用户暂时只需要一种语言，把另一语言作为后续模块，不阻塞核心发布。

## 写作标准

- 先给结论，再给技术细节
- 使用用户任务语言，不使用内部项目黑话
- 给每个状态明确证据
- 避免夸张最高级和无法验证的数字
- 中文标题和列表保持简洁，不堆装饰性句号
- 安装命令、路径和代码块必须可复制
- 所有图片都提供有意义的替代文本
